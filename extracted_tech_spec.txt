7. Risk Explanation
Do not show an arbitrary AI-generated number as the primary result.
Instead explain:
Impact Areas
Architecture
Dependencies
APIs
Data
Business Rules
Security
Tests
Example:
Impact: HIGH
Reason:
PaymentService is directly used by 4 modules and
participates in 3 business rules.
The component also writes payment status
to the orders collection.
Recommended approach:
Introduce an adapter layer before replacement.
8. Ask Why
The user can select any graph node and ask:
Why does this exist?
The system should search:
source code
imports
callers
comments
configuration
tests
Git history where available
Response format:
Why does PaymentService use LegacyGateway?
Evidence
1. src/payment.js:18
   LegacyGateway is imported.
2. src/payment.js:45
   PaymentService calls LegacyGateway.charge().
3. tests/payment.test.js:22
   Expected gateway response format is asserted.
Conclusion
The dependency appears to be required by the
current payment flow.
Confidence: High
If there is no evidence:
I could not find sufficient evidence to determine why
this dependency exists.

21. Acceptance Criteria
The prototype is considered successful only if:
Repository
Demo repository loads successfully.
Repository files can be inspected.
Analysis produces real results.
Knowledge
Dependencies are extracted.
Business rules are extracted.
Source evidence is displayed.
Confidence is displayed.
Architecture graph works.
Simulation
User can select a component.
User can run impact analysis.
Affected components are identified.
Business rules are connected.
Tests are connected.
Recommendations are generated.
AI
User can ask questions.
AI answers using repository context.
Answers cite evidence.
AI does not invent unavailable information.
Modernization
Mission can be created.
Mission has phases.
Human approval is required for important changes.
Changes can be inspected.
Verification
Tests can run.
Results are real.
Behavioral contracts are shown.
Before/after state is visible.
UX
UI looks production-quality.
No broken buttons.
No placeholder lorem ipsum.
No fake metrics presented as real.
Loading/error states exist.
Empty states exist.
22. Hackathon Demo Principle
Do not try to demonstrate every feature.
The strongest sequence is:
UNDERSTAND
     ↓
WHY?
     ↓
WHAT IF I CHANGE THIS?
     ↓
RECOVER
     ↓
VERIFY
That single story should make the product understandable within seconds.
