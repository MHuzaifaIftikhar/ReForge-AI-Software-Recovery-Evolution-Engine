1. Executive Summary
ReForge is an AI-powered software recovery and evolution engine designed to help developers understand, maintain, and safely modernize legacy software.
Traditional AI code modernization tools focus primarily on:
"Take this old code and rewrite it using newer technology."
ReForge addresses a deeper problem:
Companies don't just have legacy code. They have legacy knowledge trapped inside that code.
When developers inherit an old system, they often do not know:
why certain code exists
which components depend on it
what undocumented business rules are hidden inside it
what will break if they modify it
which dependencies are actually safe to remove
which behavior must be preserved
why previous developers made unusual architectural decisions
ReForge reconstructs this hidden knowledge and turns it into an interactive software intelligence layer.
It provides four major capabilities:
Understand — reconstruct the architecture, dependencies, business rules and behavior of a legacy codebase.
Simulate — determine what could be affected by a proposed change.
Recover — create and execute a controlled modernization mission.
Verify — prove that important existing behavior has not been unintentionally broken.
2. Core Value Proposition
One-line pitch
ReForge helps developers take ownership of software nobody understands by reconstructing its architecture and business knowledge, simulating change impact, safely modernizing it, and verifying that behavior still works.
Short pitch
ReForge doesn't just modernize legacy code. It recovers the knowledge trapped inside it.
3. Problem
Legacy software creates a significant maintenance burden.
A developer joining an old project may face:
outdated dependencies
undocumented architecture
missing tests
hidden business rules
tightly coupled modules
security weaknesses
obsolete APIs
confusing naming
dead code
undocumented external integrations
database dependencies
years of accumulated technical debt
The dangerous part is that simply changing old code can introduce regressions.
A developer may think:
"This function isn't used anywhere. I can delete it."
But it may actually be:
dynamically imported
referenced by a configuration file
triggered by a webhook
required by a scheduled job
depended upon by an external service
implementing an undocumented business rule.
Therefore, modernization requires understanding before changing.

6. Core Product Concepts
6.1 Software Knowledge Graph
The Knowledge Graph is the central intelligence layer.
It represents relationships such as:
Application
 ├── Service
 │    ├── Function
 │    │    ├── Database Query
 │    │    ├── API Call
 │    │    └── Business Rule
 │    │
 │    └── Dependency
 │
 ├── Database
 │
 ├── External API
 │
 ├── Security Boundary
 │
 └── Test
Each node should contain evidence from the repository.
Example:
{
  "type": "business_rule",
  "description": "Senior customers receive a 15% discount for orders above $500",
  "source": "src/services/pricing.js:42-47",
  "confidence": 0.94
}
The system must distinguish:
confirmed facts
inferred relationships
uncertain findings
7. Business Rule Discovery
This is one of ReForge's primary differentiators.
The system scans code for logic that appears to represent business behavior.
Example:
if (customer.age >= 60 && order.total > 500) {
    discount = 0.15;
}
ReForge converts this into:
Potential Business Rule
Senior customer discount
Customers aged 60 or above receive a 15% discount when their order exceeds $500.
Source: pricing.js:42-44
Confidence: High
Evidence: Conditional business logic
The developer can then:
accept
reject
investigate
add a note
Accepted rules become part of the project's institutional memory.
8. Change Impact Simulation
This is the primary "wow" feature.
The developer selects:
PaymentService
and asks:
What happens if I replace PaymentService?
ReForge traces the dependency graph.
Example:
PaymentService
      │
      ├── CheckoutController
      │
      ├── OrderService
      │
      ├── RefundService
      │
      ├── PaymentWebhook
      │
      ├── PaymentDatabase
      │
      ├── Payment Tests
      │
      └── Business Rules
The system produces:
Change Impact
Directly affected
PaymentService
CheckoutController
RefundService
Indirectly affected
OrderService
Payment webhook
Payment database records
Business rules affected
Payment retry policy
Refund eligibility
Failed-payment order handling
Tests affected
checkout tests
refund tests
payment integration tests
Security considerations
payment credential handling
webhook authentication
Recommended action
Introduce a payment adapter before replacing the provider.
9. Software Archaeology
ReForge should attempt to answer:
"Why is this weird code here?"
Where repository history is available, inspect:
commits
commit messages
file history
changes surrounding the component
dependency history
Example result:
This workaround was introduced when the payment provider changed its response format.
The answer must include evidence.
If evidence is unavailable, ReForge must explicitly say:
"No historical evidence found."
It must never invent a historical explanation.
10. Behavioral Contracts
When a project has poor tests, ReForge should derive behavioral expectations from existing code.
Example:
Behavioral Contract
Input:
customer.age >= 60
order.total > 500
Expected:
discount = 15%
These contracts can later be used to compare legacy and modernized behavior.
11. Recovery Mission
Instead of allowing the user to perform random modernization actions, ReForge creates a structured mission.
Example:
Mission
Modernize payment infrastructure
Phase 1
Analyze architecture.
Phase 2
Identify dependencies.
Phase 3
Recover payment-related business rules.
Phase 4
Identify affected components.
Phase 5
Create migration strategy.
Phase 6
Request human approval.
Phase 7
Apply changes.
Phase 8
Generate/run verification tests.
Phase 9
Produce final report.
12. Human Decision Gates
AI must not silently make high-impact assumptions.
When uncertainty exists:
⚠ Human Decision Required
ReForge found behavior that appears intentional but is not documented.
Detected:
Legacy payment retry mechanism
Evidence:
payment.js:91-103
What should happen?
[ Preserve behavior ]
[ Remove behavior ]
[ Investigate ]
The user's decision becomes part of the project's institutional memory.
